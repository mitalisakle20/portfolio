Salesforce Claims & eWarranty Automation Platform

A governed claims warehouse and ERP-readiness framework for complex Salesforce warranty data—combining idempotent ingestion, claim-level modeling, exception queues, data-quality controls, and human-controlled release gates.

48,026 claims · 0 duplicate IDs · 23,707 repair claims modeled · 10,499 technically ERP-ready
  • SQL Server
  • Salesforce
  • SSIS
  • Stored Procedures
  • Idempotency
  • Data Quality
  • ERP Readiness
View case study
Business problem
The Salesforce claims source held ~200 fields with sparse, overlapping, and sometimes contradictory values—no reliable, decision-ready view of a claim existed.
Scale
48,026 claims ingested · 48,026 distinct IDs · 23,707 warranty-repair claims · 10,499 technically ERP-ready · 1,164 ERP review · 3,872 manual review.
Hardest decision
Where to draw the automation line. I kept the pipeline reliable and set every ERP-release and money-moving decision behind a human gate rather than auto-approving claims on incomplete rules.
Architecture
Raw → Snapshot → Resolved → Fact, one decision-ready row per claim, with explicit resolution precedence for dealer, asset, serial, dates, statuses, and amounts. Source-conflict flags preserved instead of hidden.
Validation & safeguards
Idempotent raw upsert, unique DB index for permanent duplicate protection, source hashes, current-row indicators, and readiness / manual-review / ERP-review / data-quality / timeliness queues.
Result
A reliable data-and-control foundation for future ERP integration and warranty-service automation—without prematurely automating financial approvals.
Salesforce claims (raw) ↓ Snapshot + resolved (one row / claim) ↓ Fact + readiness queues ↓ Human release gate → ERP

Power Automate Integration Suite

Four production-oriented SharePoint and SQL Server workflows using scheduled synchronization, JSON batching, REST partial updates, duplicate protection, and source-specific ownership rules.

4 workflows · 643 dealers synced · ~60m → ~2m runtime
  • Power Automate
  • SharePoint
  • SQL Server
  • REST
  • OPENJSON
  • Upsert
View workflows
A · Dealer AOR JSON Batch Sync
SharePoint → Power Automate → JSON → SQL. Replaced row-by-row calls with one JSON batch processed set-based via OPENJSON; validated counts, deduplicated dealer-geography pairs, and preserved the rule that one dealer may hold multiple geographies. Runtime fell from ~60m to ~2m.
B · KRDW Dealer Master → SharePoint
SQL resolved view → REST partial updates for 643 dealers, enriched with territory / FSM / TSM / RSM. Matched on normalized account numbers, created or updated items without erasing SharePoint-managed fields, and separated dealer-program status from Active/Inactive status.
C · Prospect Dealer Sync
Daily SharePoint → SQL sync of ~89 prospect records with controlled insert/update behavior, preserving SharePoint-owned prospecting and onboarding attributes.
D · Fourth workflow
A fourth enterprise workflow across dealer master, AOR/territory, prospect, and operational SharePoint/KRDW synchronization, following the same duplicate-safe, source-ownership-aware pattern.

AEM Enterprise Market Data Pipeline

Consolidated fragmented market-data ingestion into one canonical raw layer and built a governed recent/history warehouse model with clean natural-key controls.

19M+ clean raw · 17.2M resolved facts · 0 duplicate keys
  • SQL Server
  • SSIS
  • Partitioning
  • MERGE
  • Reconciliation
View case study
Scale
19,023,845 clean raw records · 5,043,094 recent + 12,146,658 historical resolved · ~17.2M resolved fact records.
Hardest decision
Moving record classification out of competing raw tables and into governed SQL, using reporting date as the business partition and latest source-post date to resolve duplicate business keys.
Architecture
One canonical raw layer → recent and historical fact tables with natural-key uniqueness, partition constraints, and targeted indexing.
Validation
Reconciled source counts, partition counts, and fact counts end-to-end; redesigned SSIS so classification happened in SQL rather than in parallel raw tables.
Result
A single trusted source with a governed recent/history model and zero duplicate business keys.

View case study
Grain
One row per registration line, asset, and serial.
Hardest decision
Date precedence—preferring verified legacy registration dates over Salesforce migration dates, with explicit source classification for legacy / Salesforce / migration dates.
Dealer logic
Used the registration-header dealer as the registered dealer and retained asset-branch values for audit rather than silently replacing the main dealer key.
Validation
Uniqueness and referential-integrity checks before deploying into the production-oriented warehouse.
Result
An auditable registration fact with transparent date provenance.
