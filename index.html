Salesforce Claims & eWarranty Automation Platform

A governed claims warehouse with ERP-readiness controls and human-controlled release gates.

48,026 claims · 0 duplicate IDs · 23,707 repair claims
  • SQL Server
  • Salesforce
  • SSIS
  • Idempotency
  • ERP Readiness
Business problem
The Salesforce claims source held ~200 fields with sparse, overlapping, and sometimes contradictory values—no reliable, decision-ready view of a claim existed.
Scale
48,026 claims ingested · 48,026 distinct claim IDs · 0 duplicate IDs after validation · 23,707 warranty-repair claims modeled · 10,499 technically ERP-ready.
Readiness, honestly stated
The 10,499 claims are technically ready only—not automatically approved, not confirmed financially approved. ERP sending is not active; a human release gate remains required.
Hardest decision
Where to draw the automation line. I kept the pipeline reliable and left every ERP-release and money-moving decision behind a human gate rather than auto-approving on incomplete rules.
Architecture
Raw → Snapshot → Resolved → Fact, one row per Salesforce claim ID, with explicit resolution precedence for dealer, asset, serial, dates, statuses, and amounts. Source-conflict flags preserved, not hidden.
Result
A reliable data-and-control foundation for future ERP integration and warranty-service automation—without prematurely automating financial approvals.
Completed

Power Automate Integration Suite

Cross-platform SharePoint and SQL synchronization with duplicate-safe, source-ownership-aware workflows.

4 workflows · 643 dealers (master) · AOR sync ~60m → ~2m
  • Power Automate
  • SharePoint
  • SQL Server
  • OPENJSON
  • REST
Business problem
Dealer, territory, and prospect data lived in separate systems and drifted out of sync, with slow row-by-row processing.
A · Dealer AOR JSON batch sync
SharePoint → Power Automate → JSON → SQL. Replaced row-by-row calls (close to 60 minutes) with one JSON batch (~2 minutes); the SQL JSON-processing step runs in ~1 second. Preserves the rule that one dealer may hold multiple geographies.
B · Dealer master → SharePoint
643 SQL dealer records synchronized with zero duplicate SQL account numbers, via normalized account-number matching and SharePoint REST partial updates that preserve unrelated SharePoint-owned fields. This flow currently takes ~15 minutes for 643 sequential records (a separate flow from the AOR sync above).
Status & branch logic
Account status is based on Active/Inactive; inactive accounts may preserve termination reason and date; branch status represents the dealer-program classification.
Result
Four duplicate-safe, source-ownership-aware workflows keeping dealer and territory data consistent across SharePoint and SQL.
Completed

AEM Enterprise Market Data Pipeline

Fragmented market-data ingestion consolidated into one canonical source and a governed recent/history warehouse.

19,023,845 raw · 17,189,752 resolved · 0 dup keys
  • SQL Server
  • SSIS
  • Partitioning
  • MERGE
  • Reconciliation
Business problem
Market data arrived through fragmented ingestion into competing raw tables, making a single trusted source impossible.
Scale
19,023,845 clean raw records · 5,043,094 recent + 12,146,658 historical = 17,189,752 total resolved records · 0 duplicate natural keys after resolution.
Hardest decision
Classifying records in governed SQL: recent vs. history is based on reporting date (recent range ends 2026-05-31), and the latest source-post date resolves duplicate natural keys.
Architecture
One canonical raw layer → separate recent and historical fact tables with natural-key uniqueness, partition constraints, and targeted indexing.
Validation
Reconciled source, partition, and fact counts end-to-end; redesigned SSIS so classification happened in SQL rather than parallel raw tables.
Result
A single trusted source with a governed recent/history model and zero duplicate business keys.
Completed

Multi-Source Shipment Warehouse

US and Canadian shipment history unified without grain-related duplication, preserving full traceability.

4,643,154 rows · US 4,196,616 · CA 446,538
  • SQL Server
  • WMS
  • CAPA
  • SSIS
  • Grain Resolution
Business problem
Shipment truth was split across WMS header/detail/delivery sources and Canadian CAPA history at different grains.
Scale
4,643,154 shipment-detail rows total — 4,196,616 US and 446,538 Canadian.
Hardest decision
Resolving grain differences across shipments, invoices, orders, and serialized units without letting joins inflate quantities or financial totals.
Architecture
Snapshot and resolved warehouse structures preserving shipment, invoice, order, serial/lot, country, and source-system traceability.
Validation
Row counts, distinct business identifiers, and source-country totals reconciled against sources.
Result
Two countries of shipment history unified with duplication-safe grain and full traceability.
